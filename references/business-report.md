# 传统报告类规范（经营管理汇报）

适用于：平台建设、经营攻坚、产品调整、数据赋能、管理汇报。
目标：把业务材料转化成逻辑清晰、信息紧凑、关系明确的演示页面。

完整示例：`examples/demo_business_report.py`（预览图在 `examples/preview/business-report-*.png`）。
示例中的业务名称、系统、规模和目标值都是示例内容，**不能当作默认事实使用**。
示例里的连线（模块间箭头、数据流向、闭环）也是按示例材料画的，代码注释写明了依据。改写时要按自己的材料重新判断，不要照搬。

**排版原则**：位置尽量由 `cols()` / `rows()` / `heading()` / `lead()` / `chevrons()` 的返回值推导，不要沿用示例里的固定数字。

---

## 1. 整体表达

每页只围绕一个主要业务问题，版面分三部分：

- **顶部**：概述背景、关键举措或核心结论（`pg.lead(..., bold=False)`，关键举措用 `<b>`，少量重点词或数字用 `<red>`）
- **主体**：用结构图、映射图或流程链表达业务关系
- **辅助区**：承载业务价值、重点方案、执行保障或实际证据

## 2. 页型选择

按本页要回答的问题选择页型，不要机械轮换版式。

| 本页要回答的主要问题 | 页型 |
|---|---|
| 依托哪些资源，形成哪些能力，带来什么价值？ | 类型一：体系架构与业务价值 |
| 存在什么问题，针对谁采取什么策略，如何达到目标？ | 类型二：专项攻坚与策略落地 |
| 数据或基础能力如何转化为一线动作，并形成反馈？ | 类型三：能力贯通与运营闭环 |

- 单页请求：选最合适的一种。
- 多页请求：每页分别选，不要求三种都出现。
- 一页同时涉及多个问题时，突出主问题，其余作为辅助内容；如果用户允许增加页数，就拆页。
- 内容是一般性的文字汇报（工作总结、情况说明）时，用 `bullets()` 写「<b>短标题：</b>具体内容」的总分结构，配合 `heading()` 分组即可。

---

## 3. 类型一：体系架构与业务价值页

示例第 3 页。**核心逻辑**：基础支撑 → 核心能力及协同机制 → 业务价值。

**布局**：顶部总述 + 下方三栏，`pg.cols([1, 2, 1], gap=0.3)`（约 25:50:25）。中部架构是视觉主体，比例可以随材料调整。每栏顶部用 `heading()` 写栏目名。

### 顶部：主题与总述
- 标题直接点明体系或业务主题。
- 一段简短总述，说明建设目标、主要举措和业务作用。关键举措加粗，少量重要数字或重点词标红。

### 左栏：基础支撑（回答「依托什么」）
- 纵向排列基础系统、平台、数据或资源，通常 2–4 组，数量由材料决定。
- 每组 = 简短名称 + 1–2 条支撑说明。
- 样式：`box(fill=LIGHT_RED)` 作底板，`label(fill=PINK, color=RED, align="l")` 作组名。

### 中栏：核心架构（回答「能力如何组织并发挥作用」）
**纵向切分方法**：先放平台名称条（高约 0.42），再用 `rows()` 按内容量切出各层，层间的 gap 用来放连线：

```python
y1 = pg.heading(rx, y0, rw, "业务价值")                     # 各栏标题下方的起点
pg.label(mx, y1, mw, 0.42, "平台名称")                      # 平台名称条
(svc_y, svc_h), (cap_y, cap_h), (base_y, base_h) = pg.rows([0.6, 1.6, 0.8], y=y1 + 0.55, h=B - y1 - 0.55, gap=0.42)
```

比例按各层内容多少调整：核心能力层通常最高；只有两层时就切两份。

按材料选用以下层次（从上到下）：
1. 顶部红色横条：体系或平台名称，`label()`
2. 服务对象层：组织、业务条线、角色或场景（圆角框横排）
3. 核心能力层：业务模块、子能力及协同关系（白底红框，模块标题用 `<red>`）
4. 基础支撑层：数据、规则、组织信息或底层系统（`WARM` 底板）

每层左侧用 `label(fill=DARK)` 标注层名。
左栏展示支撑来源的概览，中栏展示它们在体系中的具体作用，避免两处重复罗列。

**连线**要区分以下关系，并按真实逻辑设置方向和标签（`arrow(..., text="服务支撑")`）：

| 关系 | 画法 | 什么时候画 |
|---|---|---|
| 数据支撑 | 单向箭头，从数据层指向能力层 | 材料说明数据来自哪些系统或底座 |
| 数据交换 | 双向箭头 `both=True` | 材料明确写了双向同步或回写；否则一律用单向「数据支撑」 |
| 服务支撑 | 单向箭头，从能力层指向服务对象 | 平台为哪些对象提供服务 |
| 业务协同 | 模块之间的箭头 | 材料写明了模块之间的先后或流转（如「指标—考核—薪酬」链条） |
| 结果反馈 | 虚线回指 | 材料写明了结果回流 |

材料里没有依据时，不要补画接口、模块间箭头或双向联动。
标签默认放在线的旁边，不会盖住箭头。连线的起止点要正好落在框边上，例如上一层的底边、下一层的顶边。

### 右栏：业务价值（回答「带来什么改善」）
- 纵向排 2–4 项，每项 = 简短标题 + 具体说明；用 `badge()` 序号或红色小标记，项与项之间用虚线分隔。
- 价值要与主要能力对应，不要重复功能名称：
  「统一查询」是功能；「减少跨系统查找，让人员信息集中可见」才是业务价值。
- 不要把业务价值画成接收数据的系统节点。

## 4. 类型二：专项攻坚与策略落地页

示例第 5 页。**核心逻辑**：现状问题 → 业务对象与机会 → 策略及动作 → 量化目标 → 执行保障。

**布局**：顶部「问题与措施」→ 中部策略主体（左，约 2.2 份宽）+ 重点方案（右，约 1 份宽）→ 底部执行要点横向展开。

### 顶部：问题与措施
- 左右两块，每块 = 红色标签（「现状和问题」/「解决措施」）+ 浅灰文字框。
- 问题：当前矛盾及其业务影响。措施：采取什么行动、面向哪些对象、预期达到什么结果。
- 问题和措施要一一对应。突出关键动作和目标，不要把背景材料全部塞进页首。

### 中部主体：对象与策略映射（回答「针对谁、用什么策略、转向什么方案」）
按材料组织为几列：
1. 客户、产品或业务对象及其规模
2. 分群条件、需求差异或策略切片
3. 对应的产品、经营动作或解决方案
4. 相关目标与指标

列头用 `label(fill=DARK)`，行与行之间用箭头表示对应关系。支持一对多、多对一的映射，但必须有材料依据。
连线过密时：合并相同路径 → 按客群分组 → 改用对应矩阵或编号关联。**不要为了显得复杂而制造交叉虚线。**

### 右侧：重点方案（回答「本次重点推动什么」）
- 红色标题条写方案名称，下方说明适用对象、差异点和预期作用。
- 价格、权益和业务规则必须来自输入材料；材料里没有时写「以正式方案为准」，不要自己编。
- 右侧用来补充主策略，不要另起一个无关的主题。

### 底部：执行要点（回答「如何落地」）
- 按实际材料分组，每组 = 短标题 + 具体动作。可选的组：策略与口径统一、渠道及触点执行、组织分工、资源或激励保障、过程监测与纠偏。
- 材料里有责任主体、执行动作和检查方式时要写明。不要强行凑成固定的三组。

### 指标表达
- 对象规模紧贴对象，目标紧贴动作。
- 保留单位、统计周期和口径。
- 区分存量规模、目标规模和已完成规模，不要混淆。

## 5. 类型三：能力贯通与运营闭环页

示例第 7 页。**核心逻辑**：数据或基础能力 → 策略形成 → 场景执行 → 结果反馈与激励。
这条链表示能力如何转化为业务结果，默认不表示时间进度。

**布局**：顶部总述 → 横向阶段链 `cols = pg.chevrons(...)` → 在每个阶段下方用返回的 `cols` 分栏展开。
通常 3–5 个阶段，默认从 4 个开始，实际数量由业务逻辑决定。阶段节点与下方内容列一一对应。
某一列内容明显更多时，用 `ratios` 加宽，例如 `chevrons(..., ratios=[1, 1, 1.3, 1])`。
各列条目数相同时，用同一组 `rows()` 切分，让各列的行横向对齐；条目数不同时，各列分别切分，不必强行对齐。
底部要画闭环时，内容列的底边留到 `B - 0.5` 左右。

### 第一列：数据与基础能力（回答「判断和行动的依据从哪里来」）
数据来源及覆盖范围、标签 / 指标 / 模型、预测或分析能力、数据团队与协作机制。
要说明这些能力如何支撑业务判断，不要只堆砌数据量。

### 第二列：策略与规则（回答「如何把数据转化为可执行的决策」）
客户识别与分群 → 策略匹配 → 规则配置 → 策略输出与分发 → 执行评价及优化。按业务关系组织，不要求全部出现。
要讲清楚策略如何进入后续的业务场景：
- 有先后顺序的步骤：纵向排列，加向下箭头。
- 并列的几类策略（如「到期续约」和「增值推荐」）：放在同一个分组框里并排或上下排列，不加箭头。

### 第三列：场景与一线动作（回答「谁在什么场景下执行什么动作」）
结构：场景名称（`label(fill=PINK, color=RED)`）+ 适用对象或工具（灰字）+ 具体动作（加粗）。同类场景按行排列，便于比较。
场景名较长、或动作说明较多时，不要把场景名放在左侧窄标签里（容易被挤成多行），改成放在每行顶部的色带。
场景分类来自材料，不要照搬示例里的厅店、装维、外呼等名称。

### 第四列：结果、反馈与激励（回答「如何看到结果，并推动后续行动」）
业务结果回传、执行进度监测、异常提醒、绩效核算、激励发放、策略迭代。

**闭环**：只有材料里确实存在反馈机制时，才画返回线：`pg.loop(cols[3], cols[1], top=内容底边, text="…")`。只有顺序传递时，不要强行说已形成闭环。
**闭环指向「被反馈优化的对象」**：
- 「驱动策略迭代」→ 指向策略列
- 「按月优化模型」→ 指向数据 / 模型所在的列
- 「调整激励规则」→ 指向规则所在的列

### 证据使用
系统截图、消息通知和案例结果用来支撑具体论点：
- 裁切到关键区域，保证文字看得清（`pg.image()`）。
- 配一句说明，指出截图证明了什么，不要让读者自己去读整张截图。
- 没有实际证据时，用机制说明代替，不要伪造截图或落地成果。

## 6. 视觉要点（在 SKILL.md 通用规范的基础上）

- 红色用于主框架、关键动作、重点数字和主要节点；蓝色（`BLUE`）只少量用于辅助说明和策略信息。
- 浅灰、暖灰、浅红、浅蓝用于辅助分区；控制嵌套边框的层数。
- 传统报告类页面中，`<red>` 用于强调。如果页面里出现「实际值对比目标」这类经营评价数字，这些数字仍按「好红差绿」规则着色。

## 7. 文案与事实

- 模块标题要短，正文写清对象、动作和作用；用具体的业务语言，不用抽象口号代替实际内容。
- 区分现状、规划、预期价值与已验证成效。
- 不编造系统关系、客户规模、价格、收益或完成率；缺少指标时用有依据的定性说明，缺少次要材料时简化对应模块。
