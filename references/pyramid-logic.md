# 金字塔沟通与逻辑关系（两类报告通用）

本规范适用于数据分析类和传统报告类。数据分析类的数字规则见 [data-analysis.md](data-analysis.md)，传统报告类的页型见 [business-report.md](business-report.md)。

完整示例：`examples/demo_logic_patterns.py`（预览图 `examples/preview/logic-patterns-*.png`），用一份「提升宽带续约率的方案建议」演示金字塔结构和五种逻辑关系。

---

## 1. 金字塔原则（芭芭拉·明托，麦肯锡）

| 规则 | 含义 | 落到 PPT |
|---|---|---|
| **结论先行** | 先说结论，再说理由 | 核心结论页放在最前；每页先写 `lead()` 结论条 |
| **以上统下** | 上层观点是下层观点的概括；下层回答上层引发的疑问（为什么？怎么做？凭什么？） | 页面标题和结论条概括本页主体；主体只放支撑这个结论的内容 |
| **归类分组** | 同一组观点属于同一逻辑范畴，相互独立、完全穷尽（MECE）；每组 2–5 个，3 个最常见 | 并列论点、章节划分、原因拆解都要 MECE |
| **逻辑递进** | 同组观点按一种顺序排列：时间（步骤先后）、结构（部分 / 区域）、重要性（从高到低） | 章节顺序、论点顺序、表格行顺序都要能说出排序依据 |

两种组织方式：

- **归纳（并列）**：几个同类论据共同支撑一个结论。这是首选方式，用于关键支撑线。
- **演绎（推理）**：大前提 → 小前提 → 结论，或者因 → 果。只在解释因果时使用，链条不超过 4–5 步，否则读者跟不上。

## 2. 搭建故事线

### 自上而下（结论已经比较清楚时）

1. **明确读者和问题**：汇报给谁？他需要做什么决定？
2. **写塔尖**：一句话答案。读者只看这一句，也知道结论或建议是什么。
3. **写开场 SCQA**：
   - 背景（S）：读者认可的事实
   - 冲突（C）：发生了什么变化或问题
   - 疑问（Q）：由此引出的问题
   - 答案（A）：就是塔尖

   SCQA 通常浓缩成核心结论页的结论条，或者封面后第一页的开场。
   变体：开门见山 A-S-C（领导时间紧时）、突出忧虑 C-S-A（风险预警类）。
4. **写关键支撑线**：回答塔尖引发的疑问（为什么要做？做什么？先做哪个？怎么保障？），共 2–5 个、MECE。每个支撑点成为一页或一个章节。
5. **往下展开**：每个支撑点向下展开证据，直到数据或事实。

### 自下而上（材料多、结论还不清楚时）

罗列所有要点 → 按 MECE 分组 → 每组提炼一句**判断**（不是标签）→ 从各组判断中提炼出塔尖。

### so what 检验

每个概括句都必须是实质结论：

- ❌「存在三个问题」「收入情况分析」「方案对比」：只是标签
- ✅「续约率下滑正在拉低渗透率」「『提速+权益』续约综合最优」：判断句

## 3. 落到 PPT

### 整份报告的结构（唯一规则，其他文档以此为准）

内容页不含封面、目录页、结束页。

| 内容页数 | 结构 |
|---|---|
| 1–3 页 | 不单设核心结论页，也不放目录。第一页的结论条写整份报告的结论；行动建议放在最后一页底部的 `takeaway()` 条 |
| 4 页及以上 | 封面后先放**核心结论页**（塔尖 + 关键支撑线，用 `pyramid()` 或 `conclusions()`），再放各支撑页 |
| 目录页 | 只有报告分成若干章、且至少一章有 2 页以上内容时才放：核心结论页之后放 `toc(active=0)`（兼作总览），之后每进入新的一章前再放一次，`active` 依次递增。每个支撑点只占一页时，核心结论页本身就是目录，不再放目录页 |

「下一步 / 需决策事项」只能写由分析直接推出的方向；具体目标值、责任部门、完成时间必须来自材料，没有就不写。

| 金字塔层级 | PPT 位置 | 方法 |
|---|---|---|
| 塔尖 | 核心结论页的结论条；内容页 ≤3 页时写在第一页的结论条 | `lead()` |
| 关键支撑线 | 核心结论页上的并列论点；各章节 | `pyramid()` / `conclusions()`；`toc()` |
| 每个支撑点 | 一页内容页的标题 + 结论条 | `page()` + `lead()` |
| 证据 | 页面主体 | 图表、表格，以及下面五种逻辑关系组件 |

- **标题即观点**：写「一、为什么要做：续约率下滑正在拉低渗透率」，不写「一、续约率分析」。
  传统报告类按其规范，标题可以只点明体系或业务主题（如「一、薪酬激励一体化平台」），但这时结论条或总述必须是判断句。
- **结论条必须是判断句**，包含关键数字。页面不用 `lead()` 时（如专项攻坚页用「现状和问题 / 解决措施」代替），用 `pg.lead_text = "一句话结论"` 登记，否则故事线里会提示「缺少结论」。
- **串读检验**：`deck.save()` 会打印故事线，即每页的标题和结论，目录页会显示章节名和当前章节。只读这一串，应能讲通整份报告；并检查顺序是否符合你选定的递进顺序，章节是否与目录一致。
- **底部结论条**：「启示 / 下一步 / 建议」用 `top = pg.takeaway(...)`，它返回结论条的上边界，主体组件用它来限定底边，不要手算高度。

## 4. 选择逻辑关系

先问「这一页要回答什么问题」，再选关系和组件：

| 这一页要回答 | 逻辑关系 | 组件 | 示例 |
|---|---|---|---|
| 结论为什么成立？（几个并列理由） | 金字塔支撑 | `pyramid()`；列表式用 `conclusions()` | logic 第 2 页 |
| 问题是怎样一步步产生、传导的？ | 因果链 | `causal_chain()` | logic 第 3 页 |
| 一个结果由哪些原因构成、各占多少？ | 原因拆解 | `cause_tree()` | data-analysis 第 7 页 |
| 几个方案选哪个？得失是什么？ | 对比权衡 | `compare()` | logic 第 4 页 |
| 多个事项先做哪个？ | 优先级矩阵 | `matrix()` | logic 第 5 页 |
| 机制如何循环运转、持续改进？ | 流程闭环 | `cycle()`；单向链 + 回流用 `chevrons()` + `loop()` | logic 第 6 页；business-report 第 7 页 |
| 按阶段推进 | 时间顺序 | `chevrons()` | data-analysis 第 9 页 |

**一页只用一种主关系。** 需要两种关系时，要么拆页，要么一主一次（次要关系放在侧栏或底部条）。

## 5. 各关系的严谨性要求

### 金字塔支撑 `pyramid()`

- 论点 2–5 个，满足 MECE：
  - 不重叠：同一个事实不同时支撑两个论点
  - 不遗漏：几个论点合起来，足以推出结论
- 论点写判断句；证据写数据或事实，并带比较基准。
- 论点按一种顺序排列：重要性、时间或结构。
- 下方空间可以放「需决策事项 / 下一步」，把汇报落到行动上。

### 因果链 `causal_chain()`

- **每一环都要有证据**：数据、调研或机制说明，写在箭头标签或证据卡片上。
- **区分已证实和推测**：没有数据证实的一环设 `verified=False`，画成虚线并标「待验证」，同时在 `source()` 中说明。
- **相关不等于因果**：两件事同时变化，不代表一件导致另一件；需要有机制解释或对照数据。
- 链条 3–5 环。起点应该是能干预的环节，底部的「启示」要说清从哪一环下手。

### 原因拆解 `cause_tree()`

- 各原因 MECE。分清两种数值，不能混用：
  - **变化归因**：各原因对变化量的贡献（如渗透率 −1.3pp 拆成 −0.5 / −0.6 / −0.2）。**各项之和 = 总变化**。
  - **构成占比**：问题本身的组成（如流失客户中各原因占比）。**各项之和 = 100%**，它解释的是「问题由什么构成」，不能说成「变化由什么导致」。
- 用 `assert` 校验上面的勾稽关系。
- 可以把材料里的细分原因重新归类（如按「我方可控 / 竞争 / 客户自身」），但要在说明里写出归并关系（如「修复慢 27% + 经理服务 19%」），并在 `source()` 中注明。
- **抽样数据要注明样本量**。差距小于抽样误差时，不要下「首要原因」的结论；样本约 100 户时，误差约 ±10pp。
- 首要原因设 `key=True` 突出；证据列给出数据。

### 对比权衡 `compare()`

- 所有方案用**同一组维度、同一评分标准**；用 `stars()` 时，在 `crit_header` 写明「★越多越优」，「难度」这类维度也按越多越优（越容易）给星。
- 星级同样是判断，**要在 `source()` 写明评分依据**；材料没有时注明「初评」。
- 方案的成本、投入、收入损失等预估是中性信息，不按好红差绿着色，优劣用星级表达。
- 必须明确推荐方案（`recommend`），`verdict` 要写清「选什么、为什么、**代价是什么**」。没有代价的推荐是不可信的。
- 预计值、测算值要在 `source()` 中注明「测算，需验证」。

### 优先级矩阵 `matrix()`

- 两个轴必须是**相互独立的维度**，如价值 × 难度、影响 × 紧迫。不要用两个高度相关的维度。
- **评分依据必须写在页面上**（`source()` 或旁注）：维度定义、分值区间、谁评估的。
  - 材料给了评分：照用，并写明来源。
  - 材料没有评分：由你按材料中的事实（成本、周期、覆盖面等）做初评，在 `source()` 写明「初评，待业务部门确认」，交付时请用户确认。**不要编造评估部门或会审结论。**
- 用 `highlight` 标出重点象限，并给每个象限一个处理方式（推进 / 规划 / 顺手做 / 暂缓）。
- 矩阵本身不是结论：旁边要写出行动安排。

### 流程闭环 `cycle()` / `chevrons()` + `loop()`

- 只有材料里存在「回到起点」的反馈机制时才画闭环；单向流程用 `chevrons()`。
- 每一步写清「动作 + 产出」。闭环处写明反馈什么、多久一次（如「按月复盘」）。
- 反馈指向被优化的对象（策略、模型或规则）。
- `cycle()` 的回流固定从最后一步回到第 1 步。如果反馈只回到中间某一步（例如只调整分级规则），改用 `chevrons()` 加 `loop()`，并指向对应的列。

## 6. 自检清单

- [ ] 只读故事线（标题 + 结论），能讲通整份报告，顺序有明确的递进依据
- [ ] 核心结论页的论点与各章节一一对应，没有矛盾
- [ ] 每个概括句都通过 so what 检验（是判断，不是标签）
- [ ] 每组论点、原因、章节都满足 MECE，数量为 2–5 个
- [ ] 每页只有一种主逻辑关系，所选组件与要回答的问题匹配
- [ ] 因果链每环有证据，推测已标「待验证」；原因贡献之和等于总变化
- [ ] 矩阵写了评分依据；对比写了推荐和代价；闭环有真实的反馈机制
